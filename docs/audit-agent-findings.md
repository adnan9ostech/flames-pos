## Authentication and Authorization

### tested
- Browser login (playwright/chrome) as all 6 accounts: all authenticate and land on correct first screen; cookie flags httpOnly=true, sameSite=lax, secure=true, path=/, 30-day maxAge.
- Direct-URL route-gate matrix: 68 page routes x 6 accounts + no-cookie (curl with each harvested cookie). Gate is clean - no role reaches a route its perms do not grant; unauth->/login; wrong-role->landingPath.
- Server-action invocation via Next-Action POST using action IDs from .next/server/server-reference-manifest.json (194 actions mapped to file/export).
- Cross-page action reuse: POSTing an action ID to a page it is NOT bundled for returns empty {} (not executed) - actions are per-page-bundle scoped.
- cashier cancelOrder(void) DENIED; kitchen cancelOrder DENIED - void right enforced at the action.
- manager createUser/setPermissions/deleteUser: cannot reach /users (307) and not bundled elsewhere - no self-escalation to users.
- manager saveAccount/toggleAccount on /accounts/chart (manager CAN open the page via accounts): DENIED - accounts_admin enforced at action, not just route.
- frontdesk saveDish reprice: cannot reach /menu (307); cross-page reuse to /customer returns {} - menu right holds.
- Full API matrix none/kitchen/cashier: /api/orders needs orders (kitchen 401), /api/orders/open needs pos (kitchen 401), /api/accounts/export needs accounts (kitchen+cashier 401), /api/orders/kitchen|unpaid-count|version|notifications need session only, /api/menu + /api/health public by design (200), /api/uploads 404. POST /api/menu/images 401 for none/kitchen/cashier.
- Session tamper: wrong-secret cookie REJECTED (->/login); expired cookie REJECTED. Signature + expiry verification sound.
- Route gate is cookie-trusting: a correctly-signed cookie with forged perms/role reaches the target PAGE, but every DB-backed action re-reads role/perms from DB and refuses (listUsers, saveAccount return access-denied; nonexistent-sub returns Session expired).
- token_version invalidation: admin role-change bumped tv 1->2; stale pv=1 correctly-signed cookie -> 'Session expired'; current pv=2 -> works.
- All 58 action files (55 actions.js + orderActions.js + voidActions.js + printerActions.js) grepped: every exported mutating function calls requireUser/requirePermission EXCEPT login and logout (correctly).

### could not test
- Capturing a real login-issued Set-Cookie for the created test user (login uses redirect(), so Set-Cookie is not returned on a Next-Action POST). token_version invalidation was instead proven with correctly-signed forged stale(pv=1)/current(pv=2) cookies whose payload matches what login issues.
- Cross-origin CSRF in a live browser: sameSite=lax plus the required Next-Action header make it low-risk, but a full cross-site POST attack was not exercised.

**[high] 'pos' permission is not enforced on order create/append/settle - accountant (no POS) and kitchen (kds only) can ring and settle real cash sales**
- where: src/lib/orderActions.js:76
- repro: With a kitchen cookie (kds only) POST the addOrder action (id 40238997211f474ad652d62117c8b649205e06f040) to the PUBLIC /customer page: body [{"items":[{"id":"00175062-...","name":"Beef Nihari","price":2495,"qty":2}],"payment_status":"paid","payment_mode":"cash","cash_received":7000,"order_type":"dine-in","include_tax":true,"client_request_id":"..."}]. Returns {data:{...paid...}}. Same with accountant cookie for an unpaid tab then settleOrder (id 602088d3b5bd...). /customer is public so the proxy never redirects these roles.
- impact: Roles explicitly barred from POS can create, append rounds to, and settle bills. The accountant role is documented 'Reads the money, never rings it: no POS, no voids' yet rang+settled a sale; kitchen holds only kds. Each produced a real paid order plus a posted GL sale journal and an FBR invoice number - a financial record created under an unauthorized identity. Inconsistent with the read side: /api/orders/open already requires 'pos'.
- evidence: EXECUTED. Created order 782642 (kitchen, paid Rs 6027, GL voucher SV-260904-0013) and order 959292 (accountant, settled Rs 3014, GL voucher SV-260904-0021). - suggested fix: addOrder/appendRoundToOrder/settleOrder should requirePermission('pos') (bumpOrder likely requirePermission('kds')), matching the /pos route and /api/orders/open gates, rather than requireUser() alone.

**[medium] approveVoid is an unthrottled password oracle that also reveals which manager/admin a password belongs to**
- where: src/app/pos/voidActions.js:43
- repro: With a cashier or frontdesk cookie (both have pos, neither has void) POST approveVoid (id 408ef4b4bdc7aec98790775d2ee61a5988455e9ec1) to /pos repeatedly with different pin values. 8 wrong guesses returned in 3.1s with no lockout/backoff; a correct guess still returns instantly afterward as {data:{approvedBy:"<name>"}} while wrong ones return {error:"That PIN is not a manager who can remove items."}.
- impact: Any pos-holding staffer (incl. cashier who lacks void) can brute-force manager/admin login passwords through this endpoint. Unlike login (which has per-identifier exponential backoff), approveVoid has none, the hit/miss is cleanly distinguishable, and a hit returns the owner's name - confirming both account and password. bcrypt slows but does not throttle. The PIN is the user's real login password.
- evidence: EXECUTED. 8 wrong PIN guesses as cashier: all instant, no lockout; correct guess (admin password) then returned {data:{approvedBy:"Admin"}}. Login throttle (login/actions.js backoff) is entirely bypassed on this path.
- suggested fix: Rate-limit/lock approveVoid per operator+IP (reuse the login backoff), and make the failure response non-identifying (never return the approver's name; return only success/failure).

### findings

**[high] Session cookies are forgeable: weak SESSION_SECRET + no entropy check = full auth/authz bypass (proven on running instance)**
- where: src/lib/auth/session.mjs:20
- repro: SESSION_SECRET in .env.local is the guessable literal 'local-dev-secret-0123456789abcdef0123'. Reproduced: node script re-implements sign() (base64url(payload).base64url(HMAC-SHA256(secret))), forged {sub: admin uuid, role:'admin', pv:4, perms:[...]} with NO password. curl -H 'Cookie: fbi_session=<forged>' http://localhost:3210/users -> HTTP 200 (passed route gate); calling admin-only listUsers action with the forged cookie returned the full user directory (emails, roles, permissions, last_login). pv=4 is a small enumerable integer.
- impact: Anyone who knows or guesses SESSION_SECRET can mint a valid session for any user id and act as admin with no credentials — total account takeover. requireUser() re-checks token_version (pv) and re-derives perms from the DB, but neither stops a forged cookie carrying the correct sub+pv.
- evidence: OBSERVED: forged cookie accepted, listUsers returned all 7 users' PII. The SECRET() guard (session.mjs:20) enforces only length>=32, not randomness, so a long-but-guessable secret passes. Dev secret read from .env.local.
- suggested fix: Require a high-entropy SESSION_SECRET (reject known/low-entropy values, not just length); never ship a human-readable dev secret; ensure production .env.production uses a CSPRNG value distinct from any committed/dev value and rotate the current one.

**[high] Login brute-force lockout is bypassable via attacker-controlled X-Forwarded-For header**
- where: src/app/login/actions.js:40
- repro: Throttle key = `${identifier}|${x-forwarded-for || 'local'}` (line 40-41). Replayed the real login POST for identifier=admin, wrong password. A) 10 attempts with a FIXED 'X-Forwarded-For: 8.8.8.8' → per-request times 0.27,0.27,0.27,0.27,0.27,1.29,2.29,4.31,8.32,16.28s (exponential backoff working). B) 12 attempts each with a DIFFERENT 'X-Forwarded-For: 10.0.0.<i>' → all ~0.26s, zero delay. Rotating the header defeats the lockout entirely.
- impact: The intended exponential/lockout brute-force defense is nullified by a header the client controls. Behind the production Apache proxy, mod_proxy appends the real IP to any client-supplied XFF, so the attacker-controlled prefix still makes the key unique every request — bypass holds in prod. Only bcrypt cost (~0.26s/attempt) then limits raw throughput. The unbounded in-memory attempts Map also grows per unique key (minor memory-DoS).
- evidence: OBSERVED timing above (executed via curl against localhost:3210). Confirmed the throttle DOES engage when XFF is constant and DOES NOT when XFF rotates.
- suggested fix: Derive the throttle IP from a trusted hop only (e.g. rightmost XFF entry set by your own proxy, or a fixed trusted-proxy count), not the raw client-supplied header; add an absolute per-account attempt ceiling independent of IP; bound/evict the attempts Map.

**[high] Void-approval PIN (= a manager's login password) is brute-forceable from any session, with no lockout and no failure audit**
- where: src/app/pos/voidActions.js:56
- repro: approveVoid loads every void-capable user's password_hash (line 56-60) and bcrypt-compares the submitted 'pin' against each (line 65). - evidence: OBSERVED: 12 unthrottled 200 responses as cashier; correct password accepted; source shows audit only on success.

**[medium] Raw MySQL error messages leak to the client through {error} envelopes**
- where: src/app/cityledger/actions.js:136
- repro: recordReceipt trims but does not length-cap 'memo' before INSERT. Called it (accountant session) with a 6000-char memo and a valid companyId; response body: {"error":"Data too long for column 'memo' at row 1"}. The catch returns e.message verbatim. Any caught mysql2 error follows this path across dozens of actions; FK failures return messages of the form 'Cannot add or update a child row: a foreign key constraint fails (`flames_pos_dev`.`<table>`, CONSTRAINT ...)', leaking schema, table and DB names.
- impact: Internal schema (column/table/constraint/DB names) is disclosed to any user who can trigger a DB error, aiding further attacks — contrary to the codebase's stated intent that {error} envelopes not leak internals. - evidence: OBSERVED: 'Data too long for column memo at row 1' returned to client. Same pattern present in most actions' catch blocks (return { error: e.message }).
- suggested fix: Map DB/driver errors (e.code) to safe user-facing strings before returning; never forward e.message from a mysql2 error to the client.

**[low] Order read/settle/void/append actions are not branch-scoped (harmless now; boundary gap if a branch-confined user is ever created)**
- where: src/app/orders/actions.js:38
- repro: getOrderDetail(orderId) selects WHERE o.id=? with only a 'orders' permission check and no branch filter; settleOrder/cancelOrder/appendRound/bumpOrder (src/lib/orderActions.js) call the verbs with an orderId and never compare the order's branch to the actor's branch. **[info] Served uploads lack X-Content-Type-Options: nosniff; framework version disclosed via X-Powered-By**
