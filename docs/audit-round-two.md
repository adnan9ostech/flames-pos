**[high] The live-update change token freezes every screen whenever any row's updated_at is ahead of the app's clock - reproduced in the live dev DB right now**
- src/lib/db/reads.mjs:145
- repro: 1) curl -H "Cookie: fbi_session=..." http://localhost:3210/api/orders/version -> {"version":"20370:1789577900750"} (= 2026-09-16T16:58:20.750Z) while `mysql -uroot -e 'select utc_timestamp(3)'` says 2026-09-16 12:18:33. 2) mysql -uroot flames_pos_dev -e "UPDATE orders SET status='preparing', updated_at=UTC_TIMESTAMP(3) WHERE order_number='PERFPOLL-AMP'" 3) re-read the endpoint -> byte-identical "20370:1789577900750". 4) repeat with status='ready' -> still identical. Earlier I proved the mechanism deliberately: inserted my own row with updated_at='2027-06-01', token pinned to 1811808000000, then two real status UPDATEs on a different order left it unchanged (I then reset that row's updated_at to 2026-09-15; the pin present now comes from another agent's locally-timestamped row, not mine).
- impact: The token is `COUNT(*):MAX(updated_at)`. MAX is pinned by a single future-dated row, so only INSERTs move the token (via COUNT). Every UPDATE-only change - a cook bumping a ticket, another terminal settling a bill, a void, an appended round, an availability toggle - moves nothing, and useRealtimeTable compares strings only. Result: a KDS left open all service silently stops showing bumps, and a till's Open Tabs rail silently stops reflecting bills settled elsewhere. It self-heals only when wall-clock passes the pinned value (4h40m in the state I found) or when someone navigates and remounts.
- evidence: src/lib/db/reads.mjs:145 `SELECT COUNT(*) AS n, MAX(updated_at) AS latest FROM orders WHERE branch_id = ?`; src/lib/useRealtimeTable.js:60 `const changed = lastVersion !== null && version !== lastVersion`. The in-the-wild trigger: five `UPDATE orders` sites do NOT set updated_at and rely on the column's `ON UPDATE CURRENT_TIMESTAMP(3)` - orders.mjs:413 (settle's include_tax/discount), :456 (invoice_number), :691 (channel_id), :707 (token_no), :806 (appendRoundToOrder) and fbr/afterSettle.mjs:92. CURRENT_TIMESTAMP is the CONNECTION's time_zone; pool.mjs:62 forces '+00:00' for the app, but @@global.time_zone is SYSTEM (PKT, UTC+5), so any other writer - a cPanel cron, a mysql CLI session, phpMyAdmin, a dump restore, or scripts/db/seed-users.mjs:215 and scripts/db/set-password.mjs:162 which use CURRENT_TIMESTAMP(3) - writes updated_at five hours into the future and blinds every terminal for five hours.
- fix: Do not derive liveness from a clock you do not own. Either (a) keep a monotonic counter the app owns (an AUTO_INCREMENT change-log row, or `SELECT MAX(seq)` over a per-branch bump table) or (b) bound the token to the trading day AND make it insensitive to a single outlier, e.g. `SELECT COUNT(*), SUM(UNIX_TIMESTAMP(updated_at)) FROM orders WHERE branch_id=? AND business_date >= CURDATE()-INTERVAL 1 DAY`. Separately, add `updated_at = UTC_TIMESTAMP(3)` to the five UPDATE sites above so the column never depends on the session time zone.
